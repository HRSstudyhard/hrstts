# 连续朗读（段内衔接）实测与结论

> 目标：段内每句话之间的衔接要快、减少卡顿。本文记录实测数据、修掉的缺陷与**不可回避的物理限制**。
> 相关：[TTS-AUDIO-CACHE.md](TTS-AUDIO-CACHE.md)（音频缓存）、[TTS-LATENCY-OPTIONS.md](TTS-LATENCY-OPTIONS.md)（延迟优化）。

---

## 0. 最终实测结果（本轮收尾）

| 指标 | 值 |
|------|-----|
| 句间空档（连续 14 句样本） | **平均 14 ms，最大 20 ms** |
| 崩溃（Scudo / Fatal signal） | **0** |
| 新旧朗读重叠告警 | **0** |
| 进程 PSS | ≈ **3.7 GB**（模型常驻 3.0 GB + 一份 KV 缓存） |
| 单句合成 RTF（CHUNK_FRAMES=16） | 4.7~5.5 |

> 关键前提：**预取（并发合成）当前全局关闭**（`prefetchGloballyEnabled = false`）。
> 原因见 §2 缺陷 5 —— 预取线程与朗读线程共用同一套 LiteRT 张量，曾导致 native 崩溃与内存翻倍。
> 段内衔接之所以还有 14 ms，是因为**已缓存过的句子**直接回放；首次听到未缓存句子时
> 空档 = 合成等待（受 RTF 限制，§3）。

---

## 1. 句间空档的构成

`句间空档 = 上一句播完 → 下一句出声` 的时间，由三部分组成：

```
上一句播完
   │ ① 切句开销：等上一个朗读线程真正退出（避免双声重叠）
   │ ② 音频准备：缓存命中 ≈ 0；未命中 = 整句合成时间
   │ ③ 起播开销：新建 AudioTrack + 首块写入（数十 ms）
下一句出声
```

| 场景 | 句间空档 | 说明 |
|------|---------|------|
| 缓存命中（句内逐句） | **11~42 ms** | 音频已就绪，只剩起播开销（本轮实测） |
| 缓存未命中，串行合成 | 合成时间（12~20 s） | 合成慢于播放（RTF > 1）时必然发生 |
| 切句开销 | ≤ 1 s | `WORKER_JOIN_TIMEOUT_MS = 1000`（等旧线程退出） |

## 2. 本轮修掉的 5 个缺陷（含 1 个崩溃）

| # | 缺陷 | 现象 | 修复 |
|---|------|------|------|
| 1 | **预热从未执行** | `attach` 后立刻把 ttsState 置为 Ready，而端侧宿主表还要加载约 2 s；「等一次 Ready」立即通过但 `engine.isReady` 仍为 false，预热被丢弃 → 缓存恒为空 | `ReaderViewModel` 改为**轮询重试**（40 × 500 ms）直到 `ttsController.isEngineReady` 再预热 |
| 2 | **预取被丢弃** | 旧实现「有线程在跑就丢请求」，段内一次排入十几句只会合成第一句 | `Qwen3TtsEngine` 改为 FIFO 预取队列 + 常驻预取线程 |
| 3 | **句间空档 1 s（人为）** | `worker.join(1000)` 是主因，且**它在主线程调用**（最坏阻塞 UI 1.5~3 s） | join 移入新 worker 线程，主线程立即返回 |
| 4 | **第二句起完全没声音（严重）** | `speak()` 开头把 `stopRequested` 置 true 以通知旧线程退出；新 worker 在 join 后检查该标志，**看到 true 就把自己中断掉**（第一句因 `previous == null` 不走这段所以能播） | worker 内**先清标志再检查**：`stopRequested = false` → join → 校验 `currentUtteranceId` |
| 5 | **并发合成导致 native 崩溃 + 内存翻倍** | 预取线程与朗读线程同时进 `synthesize`，共用 `TalkerState`/`mtpBuffers`/codec 缓冲 → `Scudo ERROR: invalid chunk state when deallocating`（SIGABRT）；两份 KV 缓存把 PSS 顶到 5.1 GB | 新增 `synthesisLock`（`ReentrantLock`）串行化所有合成入口；并把 `prefetchGloballyEnabled` 置 **false**（并发方案在真机复测前不再默认开启） |

## 3. 不可回避的限制

**RTF > 1 时，首次连续朗读不可能无缝。** 实测该模型在本模拟器上 RTF 4.7~5.5（官方 Pixel 8a 2.06）：

- 合成 1 句要 12~20 s，而播放 1 句只要 2.5~4 s；
- 未命中缓存的句子，空档 ≈ 合成时间；
- 缓存/预热只能消除**重复播放**的等待，无法让**第一次**连续播放变快。

> 关于 `CHUNK_FRAMES`：实测调到 24~48 能把 RTF 从 5~7 降到 3.5~3.9（codec 调用次数减少），
> 但**可中断粒度变粗**（一个块要合成数秒），切句时旧线程迟迟不退出 → 与下一句重叠、KV 缓存翻倍、
> PSS 冲到 5 GB。因此最终取 **16**（切句快、内存稳），性能靠缓存/预热摊薄。

## 4. 当前行为总结（可验收）

| 操作 | 表现 |
|------|------|
| 冷启动 → 引擎可用 | ≈ 2 s（宿主表），随后后台预加载三个图（≈ 5~15 s） |
| 启动后自动预热首段 | 引擎真正就绪后自动执行，写入 1~2 个片段到 `files/tts-pcm/` |
| 缓存命中的重读/回看/暂停继续/连续段内 | **首音 2~5 ms，句间空档 11~42 ms** |
| 未命中缓存的首次播放 | 空档 = 合成时间（受 RTF 限制） |
| 退后台 | 清空内存档（保留最近 3 条），磁盘档保留 |
| 稳定性 | 连续 14 句无崩溃、无重叠、无 underrun 累积 |

### 1.1 已做的 RTF 优化：`CHUNK_FRAMES` 16 → 48（实测有效）

编解码器每次调用有固定开销，分块越小调用越多、总耗时越长。把流式分块从 16 帧提到 48 帧：

| 指标 | CHUNK_FRAMES=16 | CHUNK_FRAMES=48 | 变化 |
|------|----------------|----------------|------|
| RTF（3 秒左右句子） | 5.0~7.1 | **3.55~3.86** | **↓ 约 40%** |
| 其中 codec 耗时 | 7.6~9.9 s | **2.6 s** | ↓ 约 70% |
| 单句总耗时 | 12~20 s | **11.2~11.4 s** | ↓ 约 20% |
| 首音延迟 | 5.2~6.8 s | 8.5~9.7 s | ↑（首块变大，符合预期） |

> 取舍：连续朗读场景优先「整句总耗时 / 更短的句间空档」，因此接受首音延迟略微变差。
> 该常量在 `app/data/tts/Qwen3TtsEngine.kt` 的 `CHUNK_FRAMES`。

## 2. 本轮修掉的 4 个缺陷

| # | 缺陷 | 现象 | 修复 |
|---|------|------|------|
| 1 | **预热从未执行** | 引擎 `attach` 后立刻把 ttsState 置为 Ready，但端侧宿主表还要加载约 2 s；「等一次 Ready」立即通过而 `engine.isReady` 仍为 false，预热被丢弃 → 缓存恒为空 | `ReaderViewModel` 改为**轮询重试**（40 × 500 ms）直到 `ttsController.isEngineReady` 为真再预热；实测日志 `预取入缓存：51 帧` |
| 2 | **预取被丢弃** | 旧实现「有线程在跑就丢请求」，段内一次排入十几句只会合成第一句 | `Qwen3TtsEngine` 改为 **FIFO 预取队列**（`ConcurrentLinkedDeque`）+ 常驻预取线程；朗读期间暂停消费（不抢 CPU） |
| 3 | **句间空档 1 s（人为）** | `worker.join(1000)` 是主因：旧线程早已结束也要等满 1 s | 参数化 `WORKER_JOIN_TIMEOUT_MS`；但**不能取太小**——实测 `join(150)` 会让新旧两次朗读重叠出声（双声），故取 1500 ms 并加「未按时退出」告警 |
| 4 | **段内不预取** | 只在播完一句后预取后 2 句，段落里后面的句子来不及准备 | `TtsController.prefetchParagraphAhead()`：**开播即把本段剩余句子全部排入队列**（上限 16 句/段） |

## 3. 不可回避的限制（本轮结论）

**RTF > 1 时，连续朗读不可能无缝。** 实测该模型在本模拟器上 RTF 4.5~7（官方 Pixel 8a 2.06）：

- 合成 1 句要 12~20 s，而播放 1 句只要 2.5~4 s；
- 因此「下一句」在上一句播完时**还没合成好**，空档 = 合成时间 − 播放时间（十几秒）；
- 预取/缓存只能消除「同一句第二次播放」的等待，**无法**让第一次连续播放变快。

这也是为什么两轮实测中，同一段 8 句的表现差异很大：
前 2 句命中预热缓存 → 空档 1.5 s；后面几句未命中 → 空档 = 合成等待。

**要让首次连续播放也连续，只能降低 RTF**，可选：

| 方案 | 预估 | 代价 |
|------|------|------|
| `CHUNK_FRAMES` 16 → 32/24 | 单句总耗时 −15~25%（codec 调用次数减半） | 首音延迟 +1.3 s 左右 |
| talker 与 codec 并行流水线 | 单句 −30~40% | 并发两图，实现复杂 |
| 更小/更高量化的模型 | 数量级 | 音质与重新导出成本 |

> 说明：模拟器只有 4 vCPU 且无 GPU，真机（8 核 + 更好内存带宽）RTF 会明显更低，
> 上述空档在真机上会更短 —— 真机数据仍是空白项（见 P3-STATUS.md）。
